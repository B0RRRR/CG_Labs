# Лекция 1. Введение и математика

## Почему Vulkan

- **Современный** — поддерживает новые возможности GPU, например аппаратную трассировку лучей.
- **Быстрый** — драйвер почти ничего не делает сам, программист напрямую управляет GPU.
- **Кроссплатформенный** — Windows, Linux, macOS, Android, iOS.
- **Гибкий** — память и ресурсы GPU распределяешь сам.
- **Параллельный** — хорошо работает на многоядерных процессорах.

## Растровая графика

**Растр** — сетка пикселей. Картинка на экране — это просто массив цветов.

**Пиксель** — это не цветной квадратик, а **значение цвета в точке сетки**. Изображение как бы непрерывное, а пиксель — его замер в конкретной точке.

Каждый пиксель хранит три компоненты: **R** (красный), **G** (зелёный), **B** (синий).

**Глубина цвета** — сколько бит отводится на один пиксель:

| Название | Бит на пиксель | Что даёт |
| --- | --- | --- |
| 8-битный | 8 | 256 цветов, палитра |
| High color | 15–16 | ~32–65 тысяч цветов, например 5 бит R + 6 бит G + 5 бит B |
| True color | 24 | по 8 бит на канал, ~16,7 млн цветов — обычный современный |
| Deep color | 30 / 36 / 48 | по 10 / 12 / 16 бит на канал — HDR и профессиональная техника |

### Как пиксели лежат в памяти

**Как собирается цвет:**
- **битовые плоскости** (древний способ) — отдельный слой для каждого бита: все нулевые биты всех пикселей вместе, все первые вместе и так далее;
- **чередование (interleaved)** — компоненты одного пикселя идут подряд: `RGB RGB RGB …`. Так делают сейчас.

**В каком порядке идут пиксели:**
- **линейно** — строка за строкой;
- **кривая Мортона (Z-кривая)** — пиксели обходятся зигзагом в форме буквы Z, рекурсивно. **Зачем:** соседние по картинке пиксели оказываются рядом и в памяти, поэтому меньше промахов кэша при обращении к соседям. Так часто хранят текстуры.

## Векторы и матрицы

**Вектор** — стрелка: направление и длина.

**Матрица** — таблица чисел. Главное, что нужно знать: **матрица — это способ записать преобразование**. Умножил точку на матрицу — получил преобразованную точку. Алгебра матриц совпадает с алгеброй линейных преобразований.

## Преобразования

**Растяжение** — множители на диагонали:

```
| 3/2   0  |       по X в полтора раза,
|  0   2/3 |       по Y в 2/3
```

**Поворот** на угол θ:

```
| cos θ   −sin θ |
| sin θ    cos θ |
```

Откуда синусы: при повороте единичная стрелка оси X `(1, 0)` уезжает по окружности радиуса 1 в точку `(cos θ, sin θ)` — это и есть определение синуса и косинуса. **Столбцы матрицы — это то, куда уезжают единичные стрелки осей.**

### Перенос — проблема

Сдвиг матрицей **не записать**. Перенос — нелинейное преобразование.

**Почему:** линейное преобразование `y = A·x` всегда оставляет начало координат на месте — ноль, умноженный на любую матрицу, даёт ноль. А сдвиг перемещает и ноль тоже.

С переносом преобразование становится **аффинным**:

```
y = A·x + b        A — поворот/растяжение, b — сдвиг
```

Но `+ b` в матрицу не влезает. Решение — однородные координаты.

## Однородные координаты

К точке дописывается **четвёртая координата, равная 1**. Матрица становится 4×4, и сдвиг уходит в четвёртый столбец:

```
| 1  0  0  b1 |   | x |   | x + b1 |
| 0  1  0  b2 | · | y | = | y + b2 |
| 0  0  1  b3 |   | z |   | z + b3 |
| 0  0  0  1  |   | 1 |   |   1    |
```

Четвёртый столбец умножается на единицу и просто прибавляется. Вот и сдвиг.

### Точки и векторы различаются четвёртой координатой

```
v = (x, y, z, 0)   — вектор (направление)
p = (x, y, z, 1)   — точка (положение)
```

У вектора 0 — поэтому сдвиг на него **не действует**. Логично: направление «вверх» остаётся «вверх», куда бы его ни сдвинули.

Какие операции имеют смысл — проверяется по четвёртой координате:

| Операция | Четвёртая координата | Результат |
| --- | --- | --- |
| точка − точка | 1 − 1 = 0 | вектор (от одной точки к другой) |
| точка + вектор | 1 + 0 = 1 | точка (сдвинутая) |
| вектор + вектор | 0 + 0 = 0 | вектор |
| точка + точка | 1 + 1 = 2 | **бессмыслица** |

### Если четвёртая координата не 0 и не 1

Если пришла точка `(x, y, z, w)`, её приводят к виду с единицей — **делят всё на w**:

```
(x, y, z, w)  →  (x/w, y/w, z/w, 1)
```

Это **перспективное деление**. Его делает видеокарта сама после вершинного шейдера. Именно через него работает перспектива — см. ниже.

## Проекция 3D в 2D

У камеры есть две плоскости отсечения:
- **ближняя (near)** — всё, что ближе, не рисуется;
- **дальняя (far)** — всё, что дальше, не рисуется.

Между ними — **объём вида**: только то, что внутри, попадает на экран.

### Экран: Vulkan против OpenGL

| | OpenGL | Vulkan |
| --- | --- | --- |
| Начало координат | левый нижний угол | **левый верхний угол** |
| Ось Y | вверх | **вниз** |

### Канонический объём вида Vulkan

Это «коробка», в которую должна попасть вся видимая сцена после проекции:

```
x от −1 до 1
y от −1 до 1      (+y — вниз)
z от  0 до 1      (в OpenGL — от −1 до 1)
```

Всё, что не попало в коробку, отсекается. **Задача матрицы проекции — превратить видимую область сцены в эту коробку.**

## Ортографическая проекция

Видимая область — прямоугольный ящик от `(left, bottom, near)` до `(right, top, far)`. Его нужно превратить в каноническую коробку: **сдвинуть центр в ноль** и **растянуть до нужного размера**. Параллельность граней при этом сохраняется. Значит, матрица — это композиция сдвига и растяжения:

```
           | 2/(r−l)     0          0        −(r+l)/(r−l) |
P_ortho =  |   0       2/(b−t)      0        −(b+t)/(b−t) |
           |   0         0       1/(f−n)       −n/(f−n)   |
           |   0         0          0             1       |
```

`l, r` — левая и правая граница, `t, b` — верх и низ, `n, f` — ближняя и дальняя плоскости.

- **по X и Y**: `2/(r−l)` растягивает ширину до 2 (от −1 до 1), правый столбец сдвигает центр в ноль;
- **по Z**: `1/(f−n)` растягивает глубину до 1, `−n/(f−n)` сдвигает ближнюю плоскость в ноль.

Последняя строка `0 0 0 1` — четвёртая координата остаётся единицей, **деления нет**, размер не зависит от расстояния.

## Перспективная проекция

Видимая область теперь не ящик, а **усечённая пирамида** — расширяется от камеры. Вывод на слайдах идёт в два шага.

**Шаг 1. Сжать пирамиду в ящик.** Отдельная «матрица перспективы»:

```
| n  0    0     0  |
| 0  n    0     0  |
| 0  0  f+n   −fn  |
| 0  0    1     0  |
```

Главное здесь — **последняя строка `0 0 1 0`**: она кладёт в четвёртую координату `w = z`, то есть расстояние. После деления на w координаты x и y делятся на расстояние — **далёкое становится меньше**. Третья строка подобрана так, что точки на ближней и дальней плоскостях остаются на своих местах по глубине.

**Шаг 2. Ящик — в каноническую коробку** той же ортографической матрицей.

**Итог:** `P_persp = P_ortho · M_persp`. Если пирамида симметрична (`r = −l`, `t = −b`), всё задаётся вертикальным углом обзора θ и отношением сторон окна `a = ширина / высота`:

```
           | 1/(a·tan(θ/2))        0           0            0     |
P_persp =  |       0          1/tan(θ/2)       0            0     |
           |       0               0        f/(f−n)    −fn/(f−n)  |
           |       0               0           1            0     |
```

Откуда `tan(θ/2)`: на расстоянии n от камеры половина высоты кадра равна `n · tan(θ/2)` — обычный прямоугольный треугольник.

> **Перспектива от ортографии отличается одной клеткой.** В перспективе в последней строке стоит 1 под z — в w попадает расстояние, и на него потом делят. В ортографии там 0, а в углу 1 — w всегда единица, деления нет.

# Лекция 2. Графический конвейер

## Главные объекты Vulkan

```
Приложение → Instance → Physical Device → Logical Device → Queue ← Command Buffer
```

| Объект | Что это |
| --- | --- |
| `VkInstance` | ключ к Vulkan, вход в API |
| `VkPhysicalDevice` | сама видеокарта со списком её возможностей |
| `VkDevice` | логическое устройство — через него создаются все объекты и ресурсы |
| `VkCommandBuffer` | список команд для GPU: «нарисуй сетку из стольких-то вершин» |
| `VkQueue` | очередь, в которую отправляются командные буферы на выполнение |

Ключевая мысль: **команды не выполняются сразу, они записываются в буфер**, а буфер потом целиком уходит в очередь.

## Стадии конвейера

```
вершинные и индексный буферы
        ↓
Input Assembler        — собирает вершины из буферов
        ↓
Vertex Shader          — ПРОГРАММИРУЕМЫЙ, для каждой вершины
        ↓
Primitive Assembler    — собирает вершины в треугольники
        ↓
Clipping + деление на w — отсечение по объёму вида
        ↓
Back-face culling      — выброс граней, повёрнутых изнанкой
        ↓
Rasterizer             — какие пиксели покрыты треугольником
        ↓
Fragment Shader        — ПРОГРАММИРУЕМЫЙ, для каждого пикселя
        ↓
Depth / Stencil Test   — проверка глубины
        ↓
Color Blending         — смешивание цветов
        ↓
Framebuffer            — итоговая картинка
```

Две стадии — **программируемые** (шейдеры, ты пишешь их код). Остальные — **фиксированные**: их можно только настроить, что и делается в описании конвейера.

То же по смыслу, другими словами:

1. генерация вершин — где они, их нормали, цвета
2. преобразование вершин — повороты, сдвиги, проекция
3. сборка примитивов — какая топология
4. обработка примитивов — отсечение граней и по объёму
5. растеризация — определить фрагменты
6. обработка фрагментов — свет, интерполяция цвета
7. операции над пикселями — тесты, запись в кадр

## Общие правила API Vulkan

Все функции создания `vkCreate…`:
- первым аргументом берут `VkDevice`;
- принимают описание `Vk…CreateInfo` (одно или массив);
- предпоследним — указатель на свои аллокаторы памяти, **мы передаём `nullptr`**;
- последним — адрес, куда записать созданный объект;
- возвращают `VkResult`, его нужно сравнивать с `VK_SUCCESS`.

Почти у каждой структуры-описания:
- **`sType`** — метка типа структуры, обязательна;
- **`pNext`** — указатель на следующую структуру. Через такую цепочку подключаются расширения.

## Шейдеры

**Как компилируются:**

```
GLSL-код  →  компилятор glslc  →  байт-код SPIR-V  →  приложение на Vulkan
```

SPIR-V — промежуточный двоичный формат. Драйвер получает уже скомпилированный код, а не текст.

**Вершинный шейдер** — программа **для каждой вершины**. Обязан записать позицию в `gl_Position` в однородных координатах.

**Фрагментный шейдер** — программа **для каждого пикселя**. Выводит цвет через `layout(location = 0) out vec4` — RGBA, четыре float. `location = 0` — номер изображения, куда рисовать.

## Настройки конвейера по порядку

### Input assembler — `VkPipelineVertexInputStateCreateInfo`
Откуда брать данные вершин: из каких буферов, какие байты. Подробно — в лекции 3.

### Primitive assembler — `VkPipelineInputAssemblyStateCreateInfo`
**Топология** — как вершины собираются в примитивы:

| Топология | Как читается |
| --- | --- |
| `POINT_LIST` | каждая вершина — точка |
| `LINE_LIST` | каждые две — отрезок |
| `LINE_STRIP` | ломаная через все вершины |
| `TRIANGLE_LIST` | **каждые три — отдельный треугольник** ← у нас |
| `TRIANGLE_STRIP` | лента: каждая новая вершина + две предыдущие |
| `TRIANGLE_FAN` | веер вокруг первой вершины |

### Viewport и scissor — `VkPipelineViewportStateCreateInfo`
- **viewport** — область, **в которую масштабируется** изображение. Сделаешь меньше — картинка сожмётся.
- **scissor** — область, которая **останется** после рисования; всё за ней отрезается. Сделаешь меньше — картинка обрежется.

Указывается количество (больше нуля). Сами размеры задаются при записи команд — через динамическое состояние.

### Растеризатор — `VkPipelineRasterizationStateCreateInfo`
- `polygonMode = FILL` — закрашивать треугольники;
- `cullMode = BACK_BIT` — выбрасывать отвернувшиеся;
- `frontFace` — какой порядок обхода вершин считать лицевым;
- `lineWidth = 1.0` — толщина линий, обязана быть больше нуля.

### Порядок обхода и back-face culling
Треугольник можно обойти **по часовой** или **против часовой** стрелки. От порядка зависит, куда смотрит нормаль (векторное произведение сторон).

Нужно показывать стороны, повёрнутые к нам, и не рисовать отвернувшиеся. Для этого **в движке договариваются о порядке вершин**, а GPU выбрасывает треугольники, у которых знак векторного произведения на экране не совпал с заданным. Это **back-face culling** — оптимизация, встроенная в железо.

### Multisampling — `VkPipelineMultisampleStateCreateInfo`
**MSAA** — несколько замеров на пиксель, чтобы края были гладкими. Цвет считается один раз на пиксель, а покрытие — по нескольким точкам; частично покрытые пиксели на краях получают промежуточный цвет. Бывает 2×, 4×, 8×. У нас `SAMPLE_COUNT_1_BIT` — **выключено**, поэтому края лесенкой.

### Тест глубины — `VkPipelineDepthStencilStateCreateInfo`
Нужен, чтобы **результат не зависел от порядка рисования** треугольников.

**Буфер глубины (Z-буфер)** — отдельное изображение, где для каждого пикселя хранится глубина ближайшего уже нарисованного.

Для нового фрагмента: **его глубина меньше записанной?**
- да → пиксель закрашивается, новая глубина записывается;
- нет → фрагмент выбрасывается.

Настройки: `depthTestEnable` — проверять, `depthWriteEnable` — записывать, `depthCompareOp = LESS` — ближе побеждает.

В начале кадра буфер глубины очищается значением **1.0** — «бесконечно далеко», чтобы любой первый фрагмент прошёл.

### Смешивание цветов — `VkPipelineColorBlendStateCreateInfo`
Формула смешивания для прозрачности. Пока не нужна, но нужно указать `colorWriteMask` — разрешить запись всех каналов R, G, B, A.

### Динамическое состояние — `VkPipelineDynamicStateCreateInfo`
Параметры, которые задаются **при записи команд**, а не при создании конвейера. У нас — viewport и scissor, чтобы при изменении размера окна не пересоздавать конвейер.

### Раскладка — `VkPipelineLayout`
Какие внешние ресурсы видят шейдеры: наборы дескрипторов и push-константы.

## Цепочка кадров, рендер-проход, фреймбуфер

**Swapchain (цепочка кадров)** — несколько изображений по кругу. GPU рисует в одно, пока экран показывает другое, потом они меняются.

**`VkRenderPass`** — описание задачи отрисовки:
- **вложения (attachments)** — изображения, с которыми работаем: цвет, глубина и так далее;
- **подпроходы (subpasses)** — этапы, например сначала G-буфер, потом освещение;
- **зависимости** между подпроходами — для синхронизации чтения и записи.

**`VkFramebuffer`** — связывает описание вложений из рендер-прохода с **конкретными изображениями** (image views). Номер вложения в подпроходе соответствует `location` в шейдере.

## Запись команд кадра

```cpp
vkResetCommandBuffer(...);               // очистить командный буфер
vkBeginCommandBuffer(...);               // начать запись

VkClearValue clear_values[] = {
    { .color = {...} },                  // вложение 1: цвет фона
    { .depthStencil = { 1.0f, 0 } },     // вложение 2: глубина = 1 (далеко), stencil = 0
};
vkCmdBeginRenderPass(...);               // начать рендер-проход: какой проход, какой фреймбуфер, размер

vkCmdSetViewport(...);                   // области отрисовки и отсечения
vkCmdSetScissor(...);
vkCmdBindPipeline(...);                  // выбрать конвейер
vkCmdDraw(cmd, 3, 1, 0, 0);              // 3 вершины, 1 экземпляр, смещения 0

vkCmdEndRenderPass(...);                 // закончить рисовать
vkEndCommandBuffer(...);                 // закончить запись
```

# Лекция 3. Буферы и дескрипторы

## Вершинный и индексный буферы

**Вершинный буфер** — массив вершин модели.

**Индексный буфер** — массив целых чисел: номера вершин, из которых собираются треугольники. Количество кратно трём для треугольников.

**Зачем индексы:** соседние треугольники делят вершины. Прямоугольник из двух треугольников:
- только вершины — 6 штук, две точки повторяются;
- вершины + индексы — 4 вершины и индексы `{0, 1, 2, 2, 3, 0}`.

Общие вершины хранятся один раз.

## Атрибуты вершин

Кроме позиции, вершина может хранить:
- текстурные координаты;
- цвет;
- нормаль, касательную, бинормаль;
- индексы и веса костей для скелетной анимации;
- что угодно ещё.

Всё это — **вершинные атрибуты**.

## Интерполяция и барицентрические координаты

Данные заданы только в вершинах. Чтобы узнать значение **внутри** треугольника, GPU **интерполирует** — через барицентрические координаты.

Точка P внутри треугольника записывается как взвешенная сумма вершин:

```
P = λ0·V0 + λ1·V1 + λ2·V2,     λ0 + λ1 + λ2 = 1
```

**Вес λ** — отношение площади маленького треугольника (P и две другие вершины) к площади всего треугольника. Чем ближе P к вершине, тем больше её вес.

**Цвет P** считается с теми же весами: `C = λ0·C0 + λ1·C1 + λ2·C2`. Для отрезка это обычная линейная интерполяция.

> В ЛР1 именно так получается **градиент** на гранях: цвет задан только в шести вершинах, всё между ними посчитала видеокарта.

## Как разложить данные

| Способ | Как | |
| --- | --- | --- |
| Отдельные буферы | буфер позиций, буфер цветов, буфер текстурных координат | |
| Чередование | один буфер, вершины идут структурами подряд: `x y z r g b …` | **проще, меньше кода — у нас так** |

## Как объяснить конвейеру формат вершины

**Binding** — описывает **буфер**: номер привязки, `stride` (размер одной вершины в байтах), `inputRate = VERTEX` — сдвигаться к следующей вершине после каждой.

**Attribute** — описывает **поле внутри вершины**: `location` (номер в шейдере), `binding` (из какого буфера), `format` (тип, например `R32G32B32_SFLOAT` — три float), `offset` (смещение в структуре, `offsetof(Vertex, color)`).

В шейдерах:
- входы вершинного шейдера: `layout(location = N) in` — совпадают с `location` атрибутов;
- выходы вершинного (`out`) и входы фрагментного (`in`) должны **совпадать по типу и location**.

## Как положить данные в видеопамять

1. Создать буфер `VkBuffer`.
2. Выделить видеопамять.
3. Получить на неё указатель — **отображение (mapping)**.
4. Скопировать данные `memcpy`.

### Vulkan Memory Allocator (VMA)

Без него пришлось бы самому:
- узнавать требования буфера к памяти;
- выбирать тип памяти (только GPU, общая с CPU, ReBAR);
- выделять память и привязывать к ней буфер;
- следить за фрагментацией и утечками.

VMA делает это одним вызовом `vmaCreateBuffer` и раскладывает много ресурсов внутри крупных блоков — меньше отдельных выделений, меньше фрагментации.

Флаги, которые мы используем:
- `HOST_ACCESS_SEQUENTIAL_WRITE` — процессор будет писать последовательно;
- `MAPPED` — сразу отобразить память, указатель лежит в `pMappedData`;
- `MEMORY_USAGE_AUTO` — тип памяти выбрать автоматически.

## Uniform-буфер

Для данных, которые **не меняются в течение кадра** и одинаковы для всех вершин: матрицы, время, параметры окружения, источники света.

```glsl
layout(std140, set = 0, binding = 0) uniform GlobalUniforms {
    mat4 matrix;
} global_uniforms;
```

Размер выравнивается до **16 байт**:

```cpp
.size = (sizeof(GlobalUniforms) + 0xf) & ~0xf    // округление вверх до кратного 16
```

На слайдах буфер обновляется каждый кадр в `update`: пересчитали матрицу — скопировали в память.

## Дескрипторы

Вершинные буферы привязываются через input assembler. **Все остальные ресурсы — через дескрипторы.**

**Дескриптор** — описание внешнего ресурса: тип, номер привязки (`binding`) в шейдере, количество, в каких шейдерах виден. Название как у файловых дескрипторов в ОС, но устроено иначе — разбор в последнем разделе.

Цепочка объектов:

| Объект | Аналогия | Что делает |
| --- | --- | --- |
| `VkDescriptorSetLayoutBinding` | поле в бланке | один дескриптор: binding, тип, сколько, стадии |
| `VkDescriptorSetLayout` | бланк анкеты | набор полей |
| `VkPipelineLayout` | | ссылается на все бланки — конвейер должен о них знать |
| `VkDescriptorPool` | пачка бланков | откуда выделяются наборы; задаёт максимум наборов и дескрипторов |
| `VkDescriptorSet` | заполненная анкета | выделяется из пула по бланку |
| `vkUpdateDescriptorSets` | вписать в анкету | связать дескриптор с конкретным буфером: binding, тип, буфер, смещение, размер |
| `vkCmdBindDescriptorSets` | предъявить анкету | при записи команд привязать наборы к конвейеру |

**Сколько дескрипторов выделять в пуле:** `N × S`, где N — максимум дескрипторов этого типа в одном наборе, S — максимум наборов из пула.

# Где ЛР1 отличается от слайдов — как объяснить

Препод знает свои слайды. Если код не совпадает, спросит почему. Ответы готовы.

## 1. Матрица перспективы выглядит по-другому

**Слайд:**
```
| 1/(a·tan(θ/2))        0          0          0     |
|       0          1/tan(θ/2)      0          0     |
|       0               0       f/(f−n)   −fn/(f−n) |
|       0               0          1          0     |
```

**У нас** (`math.hpp`, функция `perspective`, `k = 1/tan(θ/2)`):
```
| k/a   0      0          0      |
|  0   −k      0          0      |
|  0    0   f/(n−f)   nf/(n−f)   |
|  0    0     −1          0      |
```

**Что сказать:** это одна и та же матрица в разных соглашениях о системе координат камеры.
- На слайдах камера смотрит вдоль **+Z**, а ось **Y уже направлена вниз**, как на экране Vulkan.
- У нас камера смотрит вдоль **−Z**, ось **Y вверх** — привычная правая система координат. Переворот оси Y делает сама матрица проекции — отсюда **минус у k**.

Если в формулу со слайда подставить `z → −z` и `y → −y`, получится ровно наша. Поэтому у нас `−1` в последней строке вместо `1`, и знаки в третьей строке другие.

То же с ортографической: на слайде `1/(f−n)` и `−n/(f−n)`, у нас `1/(n−f)` и `n/(n−f)`, и минус по Y.

## 2. `frontFace` — у нас `COUNTER_CLOCKWISE`, на слайде `CLOCKWISE`

**Что сказать:** на слайде 18 сказано — «важно договориться, какой порядок вершин соблюдается». Это не закон, а договорённость. У нас вершины всех граней октаэдра перечислены **против часовой стрелки при взгляде снаружи**, и это проверено: нормали всех восьми граней смотрят наружу. Поэтому лицевым считается обход против часовой.

## 3. Матрица передаётся push-константами, а не uniform-буфером

На лекции 3 матрица идёт через uniform-буфер и набор дескрипторов. У нас — через `vkCmdPushConstants`.

**Что сказать:**
- push-константы есть в дорожной карте курса, лекция 2: «command buffers, render passes, pipelines, **push constants**»;
- это маленький блок данных, который записывается **прямо в командный буфер** вместе с командами;
- у нас 80 байт — матрица 64 и цвет 16, — а спецификация гарантирует минимум 128;
- не нужны ни буфер, ни пул, ни раскладка, ни наборы дескрипторов — для одного объекта это проще;
- uniform-буферы и наборы дескрипторов использованы во второй лабораторной, где данных стало много.

## 4. `vkBeginCommandBuffer` и `vkCmdBeginRenderPass` не в `render`

На слайдах 30–31 в функции `render` студента записывается всё: сброс и начало командного буфера, начало рендер-прохода, рисование, конец прохода, конец буфера. У нас в `render` только рисование.

**Где у нас:** в стартовом коде, `source/graphics_internal.cpp`, функции `prepare()` (начало буфера и прохода, значения очистки) и `submitAndPresent()` (конец прохода и буфера).

**Что сказать:** исходный стартовый код у меня не запускался — пустой командный буфер уходил на GPU, были ошибки валидации. Я перенёс начало и конец записи в `prepare()` и `submitAndPresent()`, чтобы каждый кадр гарантированно имел корректный рендер-проход. Команды те же, что на слайде, просто в другом месте. Значения очистки тоже как на слайде: глубина 1.0, stencil 0.

## 5. Индексы `uint16_t`, а не `uint32_t`

**Что сказать:** вершин всего 6, 16 бит хватает с огромным запасом (до 65535), и индексный буфер вдвое меньше. Тип индексов передаётся в `vkCmdBindIndexBuffer` — у нас `VK_INDEX_TYPE_UINT16`.

## 6. Матрицы — свои

На слайде 23 используется `math::Matrix4::perspective(...)`. У нас все матрицы написаны вручную в `math.hpp`: перенос, масштаб, повороты, `lookAt`, обе проекции.

# Вопросы по лекциям — короткие ответы

**Что такое пиксель?**
Значение цвета в точке растровой сетки, три компоненты R, G, B.

**Что такое глубина цвета?**
Сколько бит на пиксель. 24 бита — true color, по 8 на канал.

**Зачем кривая Мортона?**
Соседние по картинке пиксели оказываются рядом в памяти — меньше промахов кэша.

**Почему перенос не записать матрицей 3×3?**
Линейное преобразование оставляет начало координат на месте, а перенос — нет. Поэтому вводят однородные координаты.

**Чем точка отличается от вектора?**
Четвёртой координатой: у точки 1, у вектора 0. На вектор сдвиг не действует.

**Что делать, если четвёртая координата не 1?**
Поделить всё на неё. Это перспективное деление, его делает GPU.

**Что такое канонический объём вида Vulkan?**
Коробка x и y от −1 до 1, z от 0 до 1, ось Y вниз. Матрица проекции переводит в неё видимую область.

**Чем Vulkan отличается от OpenGL по координатам?**
Y вниз вместо вверх, начало в левом верхнем углу, глубина от 0 до 1 вместо −1…1.

**Как строится ортографическая матрица?**
Сдвиг центра видимого ящика в ноль и растяжение до размера канонической коробки.

**Как строится перспективная?**
Сначала пирамида сжимается в ящик — четвёртая координата становится равной расстоянию. Потом ящик ортографической матрицей превращается в коробку.

**Назовите стадии конвейера. Какие программируемые?**
Input assembler, vertex shader, primitive assembler, отсечение и деление на w, back-face culling, растеризатор, fragment shader, тест глубины, смешивание цветов. Программируемые — два шейдера.

**Что такое SPIR-V?**
Двоичный промежуточный формат шейдеров. GLSL компилируется в него `glslc` заранее.

**Что делает вершинный шейдер? Фрагментный?**
Вершинный — для каждой вершины, обязан записать `gl_Position`. Фрагментный — для каждого пикселя, выводит цвет.

**Что такое back-face culling?**
Отбрасывание треугольников, повёрнутых изнанкой. Сторона определяется порядком обхода вершин на экране — о порядке договариваются заранее.

**Зачем буфер глубины? Чем его очищают?**
Чтобы результат не зависел от порядка рисования. Очищают значением 1.0 — «бесконечно далеко».

**Viewport против scissor?**
Viewport — куда масштабируется картинка, scissor — какая часть останется.

**Что такое MSAA?**
Несколько замеров на пиксель для гладких краёв. У нас выключено.

**Что такое swapchain, render pass, framebuffer?**
Swapchain — изображения по кругу для показа. Render pass — описание вложений, подпроходов и зависимостей. Framebuffer — привязка конкретных изображений к вложениям прохода.

**Зачем индексный буфер?**
Чтобы общие вершины соседних треугольников хранились один раз.

**Как GPU заполняет треугольник цветом?**
Интерполирует значения вершин по барицентрическим координатам — весам, равным отношениям площадей.

**Чем binding отличается от attribute?**
Binding описывает буфер: шаг между вершинами. Attribute — поле внутри вершины: формат, смещение, location.

**Как данные попадают в видеопамять? Зачем VMA?**
Создать буфер, выделить память, отобразить, скопировать. VMA выбирает тип памяти, выделяет и привязывает одним вызовом и следит за фрагментацией.

**Что такое uniform-буфер?**
Буфер для данных, постоянных в течение кадра: матрицы, время, свет. Выравнивается до 16 байт.

**Что такое дескриптор и набор дескрипторов?**
Дескриптор — описание внешнего ресурса для шейдера: тип и номер привязки. Набор — группа дескрипторов, привязывается к конвейеру одной командой. Схема: раскладка набора → пул → набор → запись ссылок на буферы → привязка при записи команд.

# Вопросы с защиты — развёрнутые ответы

## Что такое шейдеры? Зачем? Какие бывают?

**Шейдер** — небольшая программа, которая выполняется **на видеокарте** на одной из стадий графического конвейера. Пишется на GLSL, заранее компилируется в SPIR-V через `glslc`, загружается как `VkShaderModule`.

**Зачем.** Конвейер сам не знает, как ты хочешь преобразовать вершины и раскрасить пиксели — это говорит шейдер. Одна и та же программа запускается одновременно для тысяч вершин или пикселей на тысячах ядер GPU, поэтому это быстро.

**Какие бывают:**

| Шейдер | Когда выполняется | Что делает |
| --- | --- | --- |
| **Вершинный** | для каждой вершины | обязан записать `gl_Position`. У нас умножает вершину на матрицу MVP и считает цвет |
| **Фрагментный** | для каждого фрагмента (пикселя) треугольника | выводит цвет. У нас просто выводит интерполированный цвет |
| Тесселяционные (два) | между вершинным и сборкой | дробят треугольники на более мелкие |
| Геометрический | после сборки примитивов | может создавать и удалять примитивы |
| Вычислительный (compute) | вне конвейера рисования | любые расчёты на GPU — будет дальше в курсе |
| Mesh / task | вместо вершинной стадии | современная замена вершинного шейдера |
| Трассировки лучей | в отдельном конвейере | генерация лучей, попадание, промах |

В ЛР1 используются только **вершинный и фрагментный** — это обязательный минимум.

## Что такое графический конвейер?

Цепочка стадий, через которую данные проходят от вершин до пикселей:

```
Input Assembler → Vertex Shader → Primitive Assembler → отсечение + деление на w
→ back-face culling → Rasterizer → Fragment Shader → тест глубины → смешивание цветов → кадр
```

Две стадии программируемые — шейдеры. Остальные фиксированные, их можно только настроить.

В Vulkan конвейер — объект `VkPipeline`. **Все настройки задаются заранее** при создании: топология, растеризация, отсечение граней, тест глубины, смешивание, формат вершин. Драйвер один раз компилирует это под железо и потом при отрисовке ничего не проверяет. Менять на ходу можно только то, что объявлено динамическим, — у нас viewport и scissor.

## Массивы вершин. Как строится фигура?

**Всё рисуется треугольниками.** Треугольник — простейший многоугольник: он всегда плоский и всегда выпуклый, поэтому видеокарта умеет быстро его закрашивать. Любая поверхность приближается треугольниками.

Фигура описывается двумя массивами:

- **вершинный буфер** — массив вершин. У нас каждая вершина — позиция и цвет, шесть float, 24 байта, идут подряд (чередование);
- **индексный буфер** — номера вершин, по три на треугольник.

Октаэдр: 6 вершин на осях координат `(±1,0,0)`, `(0,±1,0)`, `(0,0,±1)` и 8 граней — 24 индекса. Топология `TRIANGLE_LIST`: каждые три индекса — отдельный треугольник. Без индексов понадобилось бы 24 вершины — каждая вершина октаэдра входит в четыре грани.

Как видеокарта понимает, что лежит в буфере, — через описание формата: `binding` (шаг между вершинами, 24 байта) и `attribute` (с байта 0 — позиция, с байта 12 — цвет).

## Как рендерится фигура?

**Один раз при запуске:**
1. Вершины и индексы копируются в буферы в видеопамяти.
2. Создаётся конвейер со всеми настройками и шейдерами.

**Каждый кадр, на процессоре:**
3. Из ползунков собирается матрица модели, к ней — матрицы вида и проекции, всё перемножается в одну MVP.
4. Записываются команды в командный буфер: область вывода → выбрать конвейер → push-константы (матрица и цвет) → привязать вершинный и индексный буферы → `vkCmdDrawIndexed(24)`.
5. Буфер отправляется в очередь GPU.

**На видеокарте:**
6. Input assembler по индексам достаёт вершины.
7. Вершинный шейдер — 6 раз: умножает вершину на MVP, считает цвет.
8. Вершины собираются в 8 треугольников.
9. Отсечение по объёму вида, деление на w — появляется перспектива.
10. Отбрасываются грани, повёрнутые изнанкой.
11. Растеризатор определяет, какие пиксели покрыты каждым треугольником, интерполирует цвет.
12. Фрагментный шейдер для каждого пикселя выводит цвет.
13. Тест глубины: остаётся ближайший фрагмент.
14. Цвет записывается в кадр. Поверх рисуется интерфейс ImGui, кадр показывается на экране.

## Дескрипторы

**Дескриптор** — описание внешнего ресурса для шейдера: какого он типа (uniform-буфер, storage-буфер, текстура), в какой номер привязки (`binding`) попадает, сколько их и каким шейдерам виден.

**Зачем.** Шейдер не знает, где в памяти лежат данные. Дескриптор — это «слот» в шейдере плюс ссылка на конкретный буфер.

**Цепочка объектов:**

1. `VkDescriptorSetLayoutBinding` — описание одного дескриптора;
2. `VkDescriptorSetLayout` — раскладка набора: какие дескрипторы на каких binding;
3. `VkPipelineLayout` — конвейер получает список раскладок;
4. `VkDescriptorPool` — пул, из которого выделяются наборы; в нём задан максимум наборов и дескрипторов каждого типа (`N × S`);
5. `VkDescriptorSet` — набор, выделенный из пула по раскладке;
6. `vkUpdateDescriptorSets` — в набор вписывается ссылка на конкретный буфер: какой буфер, смещение, размер;
7. `vkCmdBindDescriptorSets` — при записи команд набор привязывается к конвейеру.

**Чем это НЕ похоже на дескрипторы в ОС.** Общее только слово и идея «косвенной ссылки на ресурс». Дальше всё разное:

| | Файловый дескриптор в ОС | Дескриптор Vulkan |
| --- | --- | --- |
| Что это | номер, который ядро выдаёт процессу на открытый файл | описание привязки ресурса к шейдеру |
| Кто выдаёт | ядро при `open()` | ты сам описываешь раскладку и выделяешь из пула |
| Кто читает ресурс | сам процесс, через `read`/`write` | шейдер на GPU, программа на CPU — нет |
| Как группируются | никак, по одному | в наборы, набор привязывается целиком одной командой |
| Время жизни | пока файл открыт | наборы живут, пока жив пул |

**В ЛР1 дескрипторы не используются**: матрица передаётся push-константами. Наборы дескрипторов есть во второй лабе.

## Барицентрические координаты

Способ записать точку внутри треугольника через его вершины:

```
P = λ0·V0 + λ1·V1 + λ2·V2,      λ0 + λ1 + λ2 = 1
```

**Вес λ** — отношение площади маленького треугольника, который образуют P и две **другие** вершины, к площади всего треугольника. Чем ближе P к вершине, тем больше её вес.

На примерах:
- P совпадает с V0 → `(1, 0, 0)`;
- P в центре треугольника → `(1/3, 1/3, 1/3)`;
- P на стороне V0V1 → `λ2 = 0`.

**Зачем.** Значения заданы только в вершинах. Значение в любой точке треугольника видеокарта считает с теми же весами: `C = λ0·C0 + λ1·C1 + λ2·C2`. Так интерполируются **все** выходы вершинного шейдера — цвет, нормали, текстурные координаты. Заодно веса показывают, внутри ли точка: если хоть один отрицательный — снаружи.

Видеокарта учитывает перспективу (поправка на w), чтобы цвет не «плыл» на гранях, уходящих вдаль.

> В ЛР1 именно так получается градиент на гранях октаэдра: цвет задан в шести вершинах, всё между ними посчитано по барицентрическим координатам.

## GlobalUniforms

Пример из лекции 3 — структура с данными, общими для всего кадра, в **uniform-буфере**:

```glsl
layout(std140, set = 0, binding = 0) uniform GlobalUniforms {
    mat4 matrix;
} global_uniforms;
```

- **uniform** — значение одинаково для всех вершин и пикселей в течение кадра: матрицы, время, свет;
- **`std140`** — правила выравнивания полей: `vec3` занимает место `vec4`, всё кратно 16 байтам. Структура в C++ должна совпадать байт в байт;
- **`set = 0, binding = 0`** — набор дескрипторов номер 0, слот номер 0;
- буфер создаётся с `VK_BUFFER_USAGE_UNIFORM_BUFFER_BIT`, размер округляется до 16 байт: `(size + 0xf) & ~0xf`;
- память отображена, и каждый кадр в `update` новая матрица копируется туда через `memcpy`;
- к шейдеру подключается через набор дескрипторов.

**У нас в ЛР1** вместо этого push-константы: 80 байт пишутся прямо в командный буфер, без буфера и дескрипторов. Для одной матрицы это проще. Uniform-буферы и дескрипторы — во второй лабе.

## ImGui — что это?

**Dear ImGui** — библиотека интерфейса: окна, ползунки, кнопки, выбор цвета.

**Немедленный режим (immediate mode).** Нет объектов-виджетов, которые надо создать и хранить. Каждый кадр интерфейс описывается заново, одной строкой на элемент:

```cpp
ImGui::SliderFloat("Field of view", &field_of_view, 20.0f, 120.0f);
```

Передаёшь подпись и **адрес переменной** — ImGui сам рисует ползунок и пишет новое значение прямо в переменную. Кнопка возвращает `true` в кадр, когда её нажали, поэтому её пишут внутри `if`.

**Как подключена:**
- `imgui_impl_glfw` — берёт мышь и клавиатуру из окна GLFW;
- `imgui_impl_vulkan` — рисует интерфейс через Vulkan: у неё свои шейдеры, свой конвейер, свои буферы.

**Как рисуется.** Каждый кадр: `ImGui::NewFrame()` → наш `update()` описывает окно (функция `drawInterface`) → `ImGui::Render()` превращает интерфейс в треугольники → стартовый код рисует их **отдельным рендер-проходом поверх** нашей картинки (изображение не очищается, а дорисовывается).

То есть интерфейс — тоже обычные треугольники, просто их готовит библиотека.

## Как считается цвет?

В ЛР1 цвет проходит такой путь:

**1. Цвет вершины — на процессоре, при запуске** (`createMesh`). Берётся из координат вершины:

```cpp
color = position * 0.5 + 0.5      // координата от −1 до 1 → цвет от 0 до 1
```

Вершина `(1,0,0)` → `(1, 0.5, 0.5)` розовый, `(0,0,1)` → `(0.5, 0.5, 1)` голубой. Это доп. задание 5. Цвет уходит в вершинный буфер вторым атрибутом (`location = 1`).

**2. Вершинный шейдер — 6 раз за кадр:**

```glsl
vec3 base = mix(vec3(1.0), in_color, pc.tint.w);   // цвет вершины или белый
frag_color = base * pc.tint.rgb;                   // умножить на цвет из интерфейса
```

`tint.rgb` — цвет из `ColorEdit` (доп. задание 4). `tint.w` — флажок: 1 — брать цвет вершины, 0 — белый.

**3. Растеризатор** интерполирует `frag_color` по барицентрическим координатам для каждого пикселя треугольника — отсюда градиент.

**4. Фрагментный шейдер** выводит его: `out_color = vec4(frag_color, 1.0)` — RGBA, альфа 1.

**5. Тест глубины** решает, какой фрагмент в пикселе останется — ближайший.

**6. Запись в кадр.** Цвет хранится как float от 0 до 1, в изображении — по 8 бит на канал.
